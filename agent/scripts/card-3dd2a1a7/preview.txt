操作预览：给 main 开一个修复 PR（这行已经合进 main 了，巡检眼下是停的）

发生了什么：你 13:02（北京）把 PR #1083 合进了 main，那行 administration: read
跟着合了进去。GitHub 的合法权限清单里没有这一项，多了它，整份 box-uptime.yml 连解析
都不做，所以它现在什么都不跑。跟着一起停的不只是新加的机器巡检，还有原本每小时读心跳
的那一项，以及 #1081 刚加的站点探活。合进去之后往 main 推的两次（13:02、13:06）各产生
一次 0 秒、0 个 job 的失败运行，你收到的两封就是这个。PR 页面上没有任何一项检查会拦住
它，因为 box-uptime 本来就不在 PR 跑的那几项检查里。

做什么：以你的 GitHub 账号 andylizf，从当前 main 开一条分支
fix/box-uptime-invalid-permission-scope，推上去，然后开一个针对 main 的 PR。
只做这三步：不合并、不评论、不碰别的分支。合不合由你自己点，和你平时那些 PR 一样。

改动是三处：

一、.github/workflows/box-uptime.yml，删掉 permissions 底下的 administration: read
这一行，连同它上面那两行注释。删完这一段剩：

  permissions:
    actions: read
    contents: read

二、.github/scripts/ci-pool-health.py，读不到机器名单时的那一段，从「打一句提醒
然后当成功返回」改成「报错返回失败」，并把为什么一定会读不到写进注释。

三、这一处是这轮新加的，理由在下面：给发飞书告警那一步再加一个条件，只有当这次检查
真的点出了是哪一台机器掉了，才往群里发。改的是这一行：

  -        if: ${{ failure() && env.WEBHOOK != '' }}
  +        if: ${{ failure() && env.WEBHOOK != '' && steps.pool.outputs.problems != '' }}

为什么要加第三处：仓库昨天配好了 FEISHU_ALERT_WEBHOOK。只做前两处的话，那个巡检从
现在起每半小时红一次，而它红了就会往飞书群发一句「CI 机器掉了：见运行日志」。机器其实
好好的，它只是读不到名单。一天四十多条假告警，这个群很快就没人看了。加上这个条件之后，
读不到名单仍然在 Actions 里显红给你看，但不再喊人。

提交信息和 PR 正文都是英文，写的是同一件事，正文里附了 actionlint 的原话、两次 0 秒
失败运行的编号，以及为什么 403 一定会发生。

执行时的闸门：main 上那行必须还在（已经有人修了就中止，不重复推）；远端不能已经有
同名分支（跑过一次就中止）；补丁必须原样打上；改动只许落在上面那两个文件上；本机
actionlint 必须干净、20 个单元测试必须过。任何一条不满足都不推、不开 PR。

跑完你会拿到一个 PR 链接和它的检查状态。合进去之后：box-uptime.yml 恢复有效，每小时
的心跳巡检和站点探活重新开始跑；新加的 ci-pool 那一项会每半小时红一次，报 HTTP 403，
因为它现在确实读不到机器名单，红是实话，但它不会再往飞书发告警。要它真能查出东西，
还得给它一把有管理员权限的令牌，那件事在卡片说明里，等你拿主意。
